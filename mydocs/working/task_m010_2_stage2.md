# Task #2 Stage 2 — 유한 재시도와 복구 상태

## 원인과 변경

- baseline 69페이지에서3회 연속 `conversion_timeout`, 60,002~60,004ms를 기록했다. 마지막 계측 단계는 `page_attach:start`였다. 이전64초 실패와 같은 양상을 재현했으며, 이번 재현의 원인은60초 변환 제한이다. 과거 기록에 없는 상세 오류를 소급 확정하지 않는다.
- Cloud Tasks 전달 설정을 그대로 두고 앱의 실제 작업 시도는3회로 제한한다. 자동 재시도 중은 pending/모래시계, 최종 실패는 failed/경고와 명시적 재시도 버튼으로 구분한다.
- 수동 재시도는 실패한 작업 ID로부터 새 요청 ID를 생성한다. 카드 잠금으로 동시 클릭의 중복 작업을 막고, 이전 작업의 늦은 실패 알림이 새 작업을 덮지 못한다. 기존 PDF ready는 PNG 실패로 변경하지 않는다.
- 변환 한도는120초, 시도 전체 신호는최대5분, 작업 수명은15분으로 유한하게 제한한다. Stage3~7 분포로 재평가한다. 부모의 취소 신호는 변환 자식/브라우저와 업로드에 전달한다.
- 작업 게시 전에 별도15분 후 상태 점검 전달을 영속화한다. 마지막 worker가 종료되어 catch를 실행하지 못해도 점검 전달이 이전 작업을 failed로 확정하고 stale checkpoint를 차단한다. 해당 전달도 같은 비공개 worker/OIDC/동시1 큐를 쓴다. Slack/DB/큐가 계속 장애인 상황까지 UI 갱신을 보장하지 않는다.
- PDF 링크는 공유가 확인된 ready 상태에서 노출한다. 로컬 경로도 공유 확인 뒤 즉시 메시지를 갱신하도록 정렬했다.

## 검증

- typecheck, Slack75/75, security22/22 통과. 완료 작업 중복 실행, lease 교체,3회 소진, 종료된 작업의 deadline 복구, 민감한 예외 내용 저장 금지, 새 수동 작업, 오래된 알림과 권한 회수 계약을 포함한다.
- 기존 PDF 테스트는 공유 전 첫 update 대신 공유 완료 update를 검사하도록 변경했다. 정상 출력·접근 권한 기대값은 완화하지 않았다.
- source 변경은 아직 운영 배포하지 않았다. Cloud 반복 baseline은 고정 `7bf0ce9`/이미지로 계속되며 최종 비교에 실패 표본을 포함한다. 첫69페이지 사례 이후의 baseline 실패는 첫 시도 실패에서 검증용 queue task만 취소해 반복 변환 비용을 제한하고, 이후 성공 시간으로 오인하지 않게 기록한다.
