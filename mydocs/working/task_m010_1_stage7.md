# Task #1 Stage 7 — 문서 연결 영속화

## 변경

- Node SQLite에 team으로 구분한 카드, 원본/수정본 연결, 업로드 영수증, 준비 작업 및 관찰한 thread/file 식별 정보를 저장한다. production loadConfig는 .data/state.sqlite를 사용하고 테스트는 격리된 DB/메모리로 실행한다.
- 문서 bytes, Slack token, 편집 session, signed upload/download URL을 영속 저장하지 않는다. 원본 캐시가 없으면 같은 카드에서 현재 권한을 확인한 뒤 제한된 다운로드 큐로 재준비한다.
- 기존 origin을 카드에 결속해 주소 전환 뒤에도 검증된 예전 카드 참조를 인식한다. 알 수 없는 예전 origin의 자동 갱신을 일반 파일 권한 오류로 알리지 않는다.
- 수정본과 저장 영수증을 재시작 뒤에도 복원하며 같은 actor/parent/request ID의 저장 재시도가 성공한 업로드를 반복하지 않는다. 미확인 게시 요청은 임의로 재게시하지 않는다.

## 검증

- typecheck 통과. Slack 37개, security 22개 통과.
- 실제 임시 SQLite 파일을 닫고 다시 열어 카드·수정본·PDF 연결, 원본 재다운로드, 같은 저장 요청, 다른 사용자 및 권한 철회 검사.
- 직렬화 결과에 원본 bytes/전송 URL/Slack 토큰이 없는지 검사. 파일/워크스페이스 경계를 우회하지 않음.

## 한계와 다음 단계

현재 실행 중인 서버는 아직 교체하지 않았다. 기존 메모리 전용 서버의 소실된 카드 정보는 새 DB가 소급 복원하지 않는다. 사용자에게 전달된 편집 세션은 재시작 후 다시 카드를 열어 인증해야 한다. 응답 유실과 프로세스 중단이 임의 지점에 발생한 모든 경우의 exactly-once 보장은 선언하지 않는다. SQLite 단일 프로세스 운영을 전제로 하며 다중 instance용 DB/lock은 외부 배포 단계다.

Stage 8에서 채널 정책·설정 화면·상태 반응을 연결하고 Stage 9에서 실제 앱 권한/운영 환경에 반영한다. 사용자 요청 범위에 따라 계속 진행한다.
