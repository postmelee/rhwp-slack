# Task #2 Stage 4 — PDF 우선 표시와 완료 결과 재사용

## 구현

- 독립 변환 자식의 preview/images 출력은 document → PDF → 페이지별 PNG → end의 길이 지정 프레임이다. 부모는 헤더4KiB, PDF50MiB, PNG개별5MiB/합계25MiB, 최대10장, 페이지 순서·서명·종료·뒤따르는 데이터 제한을 검사한다.
- PDF 프레임을 받으면 같은 카드에 업로드/공유 확인/ready 갱신을 먼저 한다. 같은 파서·브라우저가 PNG를 만들며 부모는 비동기 콜백과 스트림 역압으로 처리한다. PNG 오류가 발생해도 이미 공유된 PDF는 ready를 유지한다.
- 영속 PDF 파일ID가 있으면 재생성/재업로드하지 않는다. 이미 완료된 이미지ID도 재사용하며 첫 누락 페이지부터 필요한 범위를 변환한다. 완료되지 않은 전송은 기존 업로드 영수증 조정 규칙을 따른다.
- 카드 잠금·작업 소유권·매 공유 전 권한 검사·취소는 유지한다. 파일 본문은 메모리에만 있고 메타데이터에는 저장하지 않는다.

## 발견과 회복

부분 범위 PNG를 문서의 첫 요소로 배치하면 이전 페이지의 높이에서 생기던 소수점 좌표가 달라져, 2쪽 캡처 높이가1124→1123px로 바뀌었다. 원래 페이지 크기의 빈 선행 페이지를 배치하고 기존 캡처 확대율을 적용하여 좌표 맥락을 보존했다. 선행 페이지 내용 SVG는 다시 렌더링하지 않는다. 엔진·조판·글꼴 보정은 없다. HWP/HWPX2쪽 모두 기존 PNG와 바이트 동일함을 확인했다.

## 검증

- typecheck, Slack76/76, security28/28 통과. PDF 공유 직후PNG 오류→새 worker의 이미지 전용 재시도에서PDF업로드1회·원본카드1개·정상순서1~3쪽을 확인했다.
- 실제 HWP/HWPX 변환 계약2/2: PDF콜백이 PNG보다 먼저 실행되고 부분 재시도 PNG가 원래 preview와 동일. 해당 검사는 빌드가 필요한 까닭에 test:viewer 끝과 Linux container smoke에 연결했다.
- 실제2쪽 변환 예: PDF961ms, PNG1쪽1064ms,2쪽1147ms(단일 실행; 성능 통계 아님). Slack 게시 시간은 최종Cloud비교에서 측정한다.
- 프레임 잘림·초과길이·순서오류·잘못된서명·여분출력·콜백실패 검사를 포함한다. 최초 스트림 테스트는 Node Readable의 선행 읽기를 생산자 완료로 오해하여 실패했고, 명시적 async iterator로 고쳐 소비 계약을 검증했다.
- 운영 배포 전이다. 최종 전체 출력 대조와 Cloud/native Linux 검증은Stage7에서 수행한다.
