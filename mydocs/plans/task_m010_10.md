# 첫 이미지 표시 단축·변환 환경 재사용

GitHub Issue: [#10](https://github.com/postmelee/rhwp-slack/issues/10)
마일스톤: M010

## 목적

현재 Cloud Run 사양에서 PDF 게시가 첫 PNG를 가로막는 대기를 없애고, 변환 환경의 고정 준비 비용을 재사용한다. 입력·결과 문서는 작업 동안에만 보유한다.

## 배경

#2/PR #9를 `19d33b9`로 병합했다. 한 페이지 입력의 운영 측정에서 PDF 5.880초·PNG 6.131초에 생성됐지만 PNG 업로드는 9.279초에 시작했다. WASM/브라우저를 매 변환 새로 시작한다. 선행 비교 결과는 task_m010_2_report.md에 보존한다.

## 범위

### 포함

- PDF/PNG 독립 게시와 최종 작업 회수, 중복 카드 업데이트 정리.
- 비밀값 없는 변환 전용 프로세스에서 Chromium·컴파일된 WebAssembly.Module·고정 글꼴/print helper 재사용.
- 문서별 새 JS/WASM 실행 환경과 브라우저 context, timeout/abort/crash 시 재사용 프로세스 폐기.
- 버전 고정·갱신 절차와 cold/repeated 시간·메모리·시각 전후 비교.

### 제외

- CPU/메모리/최소 인스턴스/예산 변경, VM 이전, 사용자 문서 영구 캐시, 권한 검사 완화.
- 업스트림 최신 버전 자동 배포, 이번 비교 중 rhwp 0.8.6 교체. #8의 편집기 로딩/Pages 이전.

## 설계 방향

- PDF와 PNG 업로드는 독립적으로 시작하되 카드 메타데이터 쓰기는 직렬화하고 lease 확인을 유지한다. 최종 성공/실패 전에 진행 중 업로드를 모두 회수한다.
- 부모 서버의 비밀값을 전달하지 않는 별도 프로세스에 재사용 자원을 보관한다. 문서마다 새 worker thread를 생성해 JS binding의 singleton WASM 메모리를 격리하며 컴파일된 Module만 전달한다. browser context도 매번 새로 만들고 종료한다.
- 고정 font bytes/print helper는 버전별로 재사용한다. browser context 재사용으로 문서/폰트 해석 상태를 무리하게 보존하지 않는다.
- 재사용 프로세스는 직렬 처리·유한 대기열·유한 작업 수/메모리 기준으로 교체하고 오류 시 전체 폐기한다. 서버 종료 시 하위 프로세스를 종료한다.
- `.wasm`은 휴대 가능한 원본 바이너리다. 컴파일된 Module은 살아 있는 해당 runtime 안에서만 재사용하며 VM·컨테이너 간 직렬화 파일 캐시로 취급하지 않는다.
- 업스트림 core/editor/Studio commit·JS 바인딩·WASM·font/print helper를 한 빌드 단위로 고정한다. 새 이미지 배포 시 구 runtime/cache를 교체한다.

## 리스크

- 프로세스 재사용은 메모리 누적/격리 위험이 있어 문서별 worker/context 종료 및 runtime 재생성 경계가 필요하다.
- 폰트 byte 캐시가 문서별 브라우저 font decode를 제거하지는 않는다. 처음 시작 비용과 실제 재사용 이득을 따로 측정한다.
- Slack API 지연이 변환보다 클 수 있다. 서버 준비 완료와 실제 화면 표시를 구분하며 측정 전 속도 배수를 약속하지 않는다.
