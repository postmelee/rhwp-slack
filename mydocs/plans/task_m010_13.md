# Task #13 — 편집 원본/API 지연 세분화와 중복 조회 개선

Issue: [#13](https://github.com/postmelee/rhwp-slack/issues/13), M010.

## 목적과 배경

사용자가 #8 다음 단계의 원본/API 계측·경량화 진행을 요청했다. C 운영 기준 4d26ac8의 `ensureSource`는 다운로드 전 카드 권한 확인에서 받은 파일 정보를 버리고 다시 채널/파일을 조회한다. `measured`는 worker task context 안에서만 기록하므로 편집 HTTP 요청 내부는 관찰되지 않는다.

## 범위와 설계

- 고정 operation의 편집 API context와 Slack/Firestore 단계별 시간·메모리 계측.
- 다운로드 전 SourceFile을 같은 함수 호출에서 재사용; 다운로드 뒤 fresh authorization·해시 검사는 유지.
- 원본/수정본·권한 회수·로그 비밀값 배제·동시 요청 분리 검증과 전후 호출 수 비교.
- CPU/메모리/min instance/예산·OAuth·문서 캐시는 변경하지 않는다. 운영 배포는 로컬/CI·후보 검증과 분리한다.
- PR #12가 OPEN이므로 4d26ac8에서 분리한 stacked 브랜치다. #12를 임의 병합하지 않으며 통합 전 이 의존성을 해소한다.

## 문서 위치 판단

`docs/architecture.md`에 계측 계약, `mydocs/working/task_m010_13_stage*.md`에 실행 증거, `mydocs/report/task_m010_13_report.md`에 완료 범위·한계를 둔다. 사용자 문서의 기존 docs/ 루트를 유지한다. #4의 README/외부 설치는 별도 브랜치다.

## 예상 변경 파일

`src/server/{editor-routes,slack-api}.ts`, `src/server/cloud/{application,telemetry,firestore-metadata}.ts`, 해당 Slack/보안 테스트, 위 문서.

## 단계와 검증

1. 기준 고정·계측: API context, 고정 이름의 외부 호출/metadata 계측. 로그 비식별·동시성·실패 상태 테스트.
2. 다운로드 전 중복 제거: 같은 요청의 검증된 SourceFile 반환. 다운로드 후 권한 회수·원본 해시·수정본 root 검증 유지.
3. 전체 회귀·비교·보고: typecheck, unit/Slack/security, git diff --check. 실제 Cloud 지연·월 절감액은 후보 배포 전 미측정으로 남긴다.

## 리스크

권한 검사의 합법적인 시점 간 반복을 중복으로 오인하지 않는다. raw URL, HTTP header/body, 파일명, user/team/channel/file ID, 토큰을 로그로 받지 않는다. 계측 실패는 작업 결과를 바꾸지 않으며 서로 겹치는 시간은 합산하지 않는다. Firestore transaction 시간은 내부 재시도 포함 논리 연산 시간이며 과금 read 건수와 동일하지 않다.
