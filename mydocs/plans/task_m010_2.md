# Task #2 수행계획서 — 현재 사양의 문서 준비 시간과 오류 복구

GitHub Issue: [#2](https://github.com/postmelee/rhwp-slack/issues/2) · 마일스톤 M010
선행: [#1](https://github.com/postmelee/rhwp-slack/issues/1), PR #7

## 목적·배경

현재 내부 Slack 동작과 서버 사양을 유지하면서 문서 준비 지연과 재시도 상태를 개선한다. 69페이지 문서가 약64초 작업 두 번 실패 후 세 번째 약73초 작업에서 완료됐다. 로컬14.833초는 변환만 측정한 값이라 전체 Cloud 작업과 비교하지 않는다. 기존 상세 예외가 없어 timeout을 확정 원인으로 삼지 않는다.

## 범위

- 단계별 계측과 개선 전 기준, 재시도/최종 실패·부분 성공 상태, 측정 기반 유한 변환 제한과 수동 복구.
- 성능 개선4개: **변환 코드·정적 글꼴 사전 준비 / PDF 우선 제공 / 같은 변환 결과·완료 영수증 재사용 / 제한된 업로드 병렬화**.
- 전체 편집 초기화 제한, 단계별 오류·새 Slack 진입 안내. 빈 편집기로 열리는 외부 문서 링크 개선.
- 동일 사양 비교·출력/권한/저장 회귀·별도 검증 환경·운영 반영.

제외: 사양·예산·권한 추가, 엔진0.8.6/출력 품질 변경, 문서 영구 캐시, 외부 OAuth, #3 운영 한 달 관찰, #4 Marketplace, #5 채널별 공유 해제 정책, #6 신규 PNG/ZIP 명령.

## 고정 조건과 설계 방향

- ingress1vCPU/1GiB/min1/max1, worker2vCPU/4GiB/min0/max1, 작업 동시1. 검증용 worker도 같은 CPU/메모리·동시성으로 실행하고 검증 뒤 불필요한 자원은 정리한다.
- 기존 문서 bytes는 변환/다운로드 중 메모리 또는 짧은 임시 보관만 허용한다. 메타데이터는 파일 ID·카드 ID·작업 상태·영수증·시간만 저장한다.
- 로그는 허용한 단계/오류 코드/숫자와 불투명 작업 식별자만 기록한다. 문서명·내용·이벤트 원문·토큰·업로드 URL·ticket/bearer는 금지한다. 예외 message/stack을 그대로 Cloud Logging에 쓰지 않는다.
- fresh 문서 파서/브라우저 격리를 유지한다. 사전 빌드 대상은 고정 코드·글꼴뿐이다.
- PDF 생성 후 별도 업로드/확인과 PNG 생성이 겹칠 수 있다. 공유 확인 전 준비 완료로 표시하지 않는다. PNG 실패가 공유 완료된 PDF를 실패로 되돌리지 않는다.
- 업로드 최대2개는 후보이며 순차 대비 시간·메모리·안정성을 보고 채택한다. 페이지 표시 순서와 영수증 저장 경쟁을 직렬화한다.
- 최종 실패에는 명시적 새 작업 세대로 재시도한다. 이미 완료된 작업의 deterministic queue name을 재사용해 아무 일도 일어나지 않는 경로를 피한다.
- 초기화 timeout은 호스트에서 미완성 iframe을 정리하고 재진입 안내한다. 소비된 티켓으로 자동 무한 재시도하지 않는다. 외부 링크는 인증된 사용자로 추정하지 않는다.

## 단계와 순서

1. 계측·기준 측정
2. 재시도/실패 복구
3. 변환 코드·글꼴 사전 빌드
4. PDF 우선·중복 변환/업로드 제거
5. 최대2개 업로드 비교
6. 편집 초기화·외부 문서 링크 안내
7. 전후 비교·회귀·검토·운영 반영

일반 템플릿의3~6단계보다 한 단계 많다. 사용자와 합의한 의존 순서와 각 변경의 성과를 독립 판정하기 위해7단계를 유지한다. 각 단계는 검증/보고와 함께 커밋한다.

## 검증·비교 계약

- 입력: 합성2페이지 HWP/HWPX와 문제를 보인69페이지 HWP. 동일 바이트 해시를 확인하되 문서 bytes는 Git에 보관하지 않는다.
- 측정: 권한/다운로드/프로세스 준비/파싱/렌더/PDF/PNG/업로드/공유확인/카드갱신, 첫 카드·PDF 사용가능·첫이미지·전체완료, 시도수와 메모리.
- 로컬과 Cloud Run은 별도 표. 각 입력/조건 최소3회 반복을 원칙으로 중앙값·범위·성공률을 보고한다. cold는 인스턴스 시작 로그로 확인하며 warm은 동일 인스턴스에서 처리했음을 확인한다. 변환 자식은 각 호출마다 새 프로세스다.
- baseline은 계측만 추가한 코드와 원본 운영 이미지를 구분해 기록한다. 계측 오버헤드도 제한/기록한다. queue wait와 처리 시간, 앱 내 PDF ready와 사용자가 클릭해 보는 UI 수용을 구분한다.
- Linux 같은2CPU/4GiB 자원 제한에서 검증한다. 메모리 표본 평균은 순간 peak로 쓰지 않는다. 실제 OOM·cgroup 수치·지원되지 않는 지표를 구분한다.
- 이미 준비된 PDF 후 PNG 실패, 업로드 응답유실/재시도, lease 만료, 권한 회수, 페이지 순서, 저장 중 추가 편집, 같은 스레드 유지 회귀.
- PDF/PNG 페이지/시각 출력을 같은 입력으로 대조한다. 페이지 수/바이트 해시만으로 시각 일치라고 판단하지 않는다.
- 운영 반영은 전체 자동 검사·Linux smoke·실제 Slack PDF/갤러리/Studio/저장 수용 및 동일 사양 확인 뒤 수행한다. 기존 리비전으로 되돌릴 경로를 남긴다.

## 리스크

- 더 긴 제한 시간은 처리 슬롯 점유도 늘린다. 기존60초와 측정 분포를 비교해 유한 상한을 선택한다.
- 업로드 병렬화는 순간 메모리와 상태 저장 경쟁을 늘린다. 최대2개 및 직렬화된 checkpoint를 사용하고 악화 시 순차 유지한다.
- Cloud 재시도 소진은 앱 예외뿐 아니라 컨테이너 종료도 고려해야 한다. 단순 catch 카운터만으로 모든 종료를 포괄했다고 주장하지 않는다.
- 실제 Slack API/네트워크 지연이 표본에 영향을 준다. 측정 조건과 실패 표본을 삭제하지 않는다.

## 승인 근거

사용자는 현재 사양에서4가지 개선·전후 비교·이전 권장 수정을 승인했고, 기존 이슈를 마무리한 뒤 새 이슈에 순서와 세부사항을 명시해 진행하도록 지시했다. 이 계획 범위의 단계별 구현·검증·PR·통합을 이어간다. 새 비용/권한/범위 확대는 포함하지 않는다.
